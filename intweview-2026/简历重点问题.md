##### 1. 统一路由怎么做的

项目中有一个单独配置文件：Routes.tsx，这个文件会引入所需要的路由组件， 路由组件和对应的 path 以对象形式放入一个数组中，最后导出这个数组。

##### 2. 权限是怎么做到，是依赖前端还是依赖后端

1. 权限系统是前后端配置完成的。 先讲一下云安全中的权限需求： 云安全中心会根据企业租户的付费情况，将自身提供的功能划分为免费版、基础版、付费版、旗舰版等，不同的版本提供的功能不一样。 例如，免费版只能提供基础的主机防护功能，而基线扫描、病毒扫描等功能都是付费版才有的，但是这些功能对于租户而言是可见而不可用的。也就是菜单中会存在全部的功能选项，但是对于未开通的功能，菜单名称旁边会有锁的图标，表示这个功能是是加锁的，点击以后，不会渲染对应的路由组件，而是展示该功能的介绍信息，并引导用户开通这项功能。此外，除了菜单加锁，有一些的页面中的功能也是加锁的，例如病毒扫描中的日志图谱分析功能，需要开通旗舰版才能使用。

2. 从以上的权限需求中，我们总结权限设计的几个要点：

   - **获取当前租户的版本信息**

   - **菜单加锁**

   - **统一样式的引导购买页，功能介绍和购买链接支持配置**

   - **其他场景的加锁 / 不可见**

3. 所以，这套权限系统分为两个部分：

   - 后端记录当前用户的版本信息。

   - 前端有一个单独的配置文件，文件的内容是需要加锁的路由的 path、功能介绍，哪些版本可用、不可用状态下是加锁还是隐藏等。

4. 前端获取当前租户的版本信息后，将其存入全局状态中。

5. 自定义权限 hook 函数用来检查某个路由是否具有相关权限：
   - 接收的参数是 path，根据 path 从配置文件中获取对应的权限信息。
   - hook 内部从全局状态中获取当前租户的版本信息
   - 两种信息进行对比，最终得到当前的路由是否有权限，如果没有权限，是展示引导购买页（加锁）还是不可见。
   

6. 自定义路由守卫组件，在注册路由组件时，使用路由守卫组件包裹真正的路由组件，其主要接收两个参数：path 和路由组件。

7. 路由守卫组件内部，会根据当前被包裹的组件判断是否有相关的权限，这里使用自定义权限 hook 函数判断权限。
   - 如果是加锁（没有权限），则返回引导购买页组件。
   - 如果是不可见，则返回 React-Router 提供的重定向组件，重定向到默认页面。
   - 如果有权限，则正常返回对应的路由组件。

8. 菜单导航栏使用权限 hook 函数决定某个菜单是否加锁或者是隐藏。

9. 对页面中的某些功能加锁，因为这些功能分散在不同的页面，所以暂时没法做统一配置，只能在组件层去对具体的组件加锁，目前是这样做的：
  - 获取当前页面的 path
  - 使用权限 hook 获取权限信息
  - 对组件进行加锁（不加锁）

10. 路由守卫组件：在渲染真正的路由组件前，对当前的路由进行一些操作，如权限判断、登录判断等。React-Router 并没有提供路由守卫相关的 hook，所以需要自行处理。目前的处理方式是：自定一个路由守卫组件，在注册路由组件的时候，使用路由守卫组件包裹真正的组件。

#### 2. 高级筛选表格

##### 1. 应用场景

1. 云安全中心的主机防护、病毒查杀等多个页面需要展示大量的防护日志数据，这些日志数据包含二十个以上的字段。运维人员需要对这些数据进行筛选，方便器进行研判，所以需要在传统表格的基础上附带一个包含大量筛选项的表单。

2. 核心需求包括：
   - 高频使用的筛选项放在外面。低频使用的默认隐藏，需要时可以展开。
   - 可以根据页面宽度自动调整筛选项布局。
   - 支持常见的表单组件，如下拉、文本、时间等，支持配置的方式使用表单组件。
   - 支持自定义筛选项。
   - 输入完查询条件以后，能实时展示查询结果，无需手动点击确认。

##### 2. 核心筛选实现原理

1. 核心原理是基于事件订阅/发布机制的数据传输体系。

2. 需要一个代理类，在代理类使用 state 存储表单状态（数据）。使用 event 作为事件中心，提供事件订阅、发布、移除等能力。

3. 使用 Controller 组件包裹表单项组件，Controller 组件会向表单项组件注入 value 和 change 事件处理函数，使得表单项组件成为受控组件。每个 Controller 会绑定一个 key，这个 key 作为 Controller 的唯一标识，也是作为订阅事件的事件名称。在 Controller 组件内部订阅更新事件（自定义），因为只有一个事件中心，Controller 订阅的事件都会在事件中心中注册。当数据更新时，向对应的 Controller 发送通知， Controller 收到通知后，立即更新组件。

4. 当某个表单项数据更新后，通过 Controller 的 change 处理函数同步更新至代理类的 state 中。待内部的 state 更新完成以后，在借由外部组件的 change 处理函数将最新的 state 同步至外部组件中。

5. 外部组件的数据更新后，首先同步更新到代理类的 state 中，在更新过程中，会对新旧数据进行比较，找出需要更新的字段与值。更新完成后，事件中心会根据更新的字段列表，逐一通知对应的 Controller 完成更新。

6. 代理类中的 state 更新时，同步更新 url 查询字符串。

7. 总结：
   - 代理类是核心，负责存储和更新数据、注册事件、触发事件。
   - 数据更新分成两条路：
     - 筛选项到外部：通过 Controller 的 change 处理函数同步至代理类的 state 中，待 state 更新完成，在同步到外部组件。
     - 外部到筛选项：首先会更新代理类的 state，然后会触发事件，通知对应的 Controller 更新筛选项组件。
   - 使用单例模式和 useRef 保证一个组件只能有一个代理类实例。

##### 3. 响应式布局

1. 响应式布局规则：
   - 容器宽度 1440px 及以上，一行展示 4 个筛选项，宽度自适应。
   - 容器宽度 980px - 1440px，一行展示 3 个筛选项，宽度自适应。
   - 容器宽度 980px 以下，一行展示 3 个筛选项，宽度不变，页面增加滚动条。

2. 筛选项宽度 = 容器宽度 / 一行筛选项的数量，因此需要在容器宽度发生变化的及时得知一行展示几个筛选项。

3. 在 useLayoutEffect 定义 ResizeObserver 实例，并启动对目标容器元素的观察。

4. 当容器元素的尺寸发生变化时，会触发 ResizeObserver 的回调函数，我们会计算当前的宽度下，一行适合展示几个筛选项。

5. 计算完成以后，更新组件。

6. 避免多次触发计算过程，这里使用防抖函数进行优化。

##### 4. 优势

1. 减少组件的无意义重复渲染。传统的表单组件使用受控模式，当表单组件数据变化的时候，会通过 onChange 函数传递给父组件，进而引发父组件的渲染，但是父组件渲染会引起子组件的渲染流程，虽然不会更新真实 DOM，但是也会跑一遍完整的渲染流程。当子组件比较少的时候，可能没什么问题，但是当子组件比较多的时候，就会导致组件的渲染效率变低。

2. 实现特定筛选项组件更新。更新当外部数据更新，需要同步到内部的筛选项组件的时候，我们希望特定组件更新，而不是更新全部筛选项组件。我们只需要找出更新数据的字段，然后触发以这个字段为名称的事件，就可以更新筛选项组件。传统受控模式下，会更新全部选项组件组件。

3. 根据当前页面/容器宽度自动调整页面布局，实现视觉层次的统一。

#### 3. 下单项组合组件

##### 1. 应用场景

1. 租户可以在平台上购买多种防护产品，例如主机防护、病毒查杀、基线扫描等。每种产品需要单独的下单页，保证租户可以按照需求购买他想要的防护产品。

2. 每种防护产品的可下单项目大体类似，包括购买项目、购买数量、时长、是否自动续费等。但是每个产品还有一些特殊的下单项，比如主机防护有磁盘扫描、日志上报等子项目。

3. 需要根据租户选择的数据实时计算价格。

##### 2. 如何实现

1. 一开始是将全部的下单项写在一个表单里，然后根据 url 查询参数的不同，对下单项进行展示与隐藏，从实现了每个防护产品都有一个单独的下单页的目标。

2. 但是这种方式的最大问题是维护非常麻烦：增加新下单项需要兼容以前的内容，增加新的防护产品时，需要对表单整体做调整。

3. 后面决定放弃这种实现方式，改由下单项组合的方式实现下单页功能。

4. 将通用的下单项拆分出来，形成单独的组件，如购买项目、购买数量、时长、是否自动续费这些组件，完全可以作为独立组件进行封装。

5. 将每个防护产品的下单页的表单封装为一个独立组件，这个独立的表单组件由不同的下单项组合而成。

6. 设置一个配置对象，key 为防护产品名称，value 为表单组件。

7. 固定下单页展示的内容，如下单按钮，订单金额组成、用户须知等。中间变化的只有防护产品的下单项表单。

8. 从 url 参数上获取防护产品名称，进而得到表单组件，之后渲染这个表单组件，即可展示下单页全部内容。

##### 3. 优势

1. 配置灵活，只需要写好表单组件和配置好防护产品名称即可。

2. 维护简单，只需要关注每个防护产品由自己独立的表单组件即可。

3. 出现 bug 时，方便排查，无需担心牵一发而动全身。

4. 方便对每个防护产品下单项进行调整。


#### 3. 性能优化

##### 1. 如何优化打包产物体积

1. 首屏没有比较复杂的内容，都是展现一些汇总信息，主要以表格为主，按理说页面很快就能显示出来。但是首屏加载时间较长，大约 2 - 3s 左右， 即使使用了 loading 占位，用户体验也不是很好。经过排查，发现是获取 js 的请求的时间过长，影响了页面加载。因此需要对 js 文件进行处理，减少其体积，提高加载效率。 

2. 使用 webpack-bundle-analyzer 插件分析打包产物的组成。

3. 根据分析结果，将一些第三方模块拆分出去，作为独立模块打包，降低主产物体积。因为项目中使用了 ECharts、G6 等第三方可视化库，html2canvas、jspdf 等生成 pdf 的第三库，这些库体积相对比较大，但是只在指定页面使用，所以完全没有必要打包进主产物中。

4. 将一些非 ES6 写的库替换为 ES6 写的库，这样做的的好处是充分利用 ES6 提供的 import/export 语法，以实现 tree shaking。进一步减少打包产物体积。例如，项目中使用了 lodash，默认情况下安装的是 ES5 版本，打包时会将整个 lodash 打包进主产物中。在产物分析图中，lodash 也占据了比较大的体积。但是还不能将 lodash 拆分出去，而 lodash 提供了 ES6 版本，所以将项目中的 lodash 升级为 ES6 版本。这样打包的时候只打包我们使用的部分，极大地减少了主产物地体积。

5. 对非首屏加载地第三方模块采用预加载技术，这一步也是通过插件实现。这里地预加载使用 prefetch 模式，也就是等待首屏加载完成以后，再去加载第三方模块。

##### 2. 如何提高复杂页面响应速度

1. 做过一个复杂表单项的优化工作。

2. 这个表单的作用是根据病毒查杀日志手动处理查杀结果，因此需要根据日志信息填写较多的内容。这个表单的表单项由多个组件组成，包括下拉选择、文本输入、单选输入等组件。表单项以下拉组件为主，根据选择的数据限制输入的组件类型，比如选择某个字段以后，只能输入文本。表单还具有增减表单项的功能。

3. 当需要填写的表单项较多时（多余 20 个），输入文本会就会变卡。

4. 使用 React 开发工具进行排查，发现导致变卡的原因是每次输入数据或者数据变化的时候，都会重新渲染整个表单，而不是只渲染那一个由数据输入的表单项组件。

5. 所以优化的目的就是避免无意义的渲染。优化采用了以下几种方式：
   - 给每个表单项组件加上 key。
   - React.memo 包裹表单项组件。
   - useCallback 包裹 onChange 函数，避免重新生成的 onChange 导致子组件重新渲染。
   - 调整表单项内部组件结构，使其内部组件的属性参数尽量简单，如文本输入组件，只接收 value 和 onChange 函数，其中 value 为字符串类型，这样在 value 和 onChange 函数不变的情况下，文本输入组件就不会重新渲染。

6. 通过以上几方面的优化，成功的解决了表单卡顿的问题。

##### 2. 权限是怎么做到，是依赖前端还是依赖后端

1. 权限需求：

2. 在接口层，前后端约定：
   - 后端：如果该用户没有权限，则接口返回特定的状态码和权限 id。
   - 前端：对全部的接口返回值进行拦截，接口值的状态码表示无权限，则根据接口提供的权限 id 拼接成权限申请平台的 url，然后直接跳转到权限申请页面。

3. 后端提供一个权限查询接口，根据当前用户信息查询有无该模块的操作权限。当用户访问指定页面时，前端会预先查询该用户有无操作权限：
   - 有权限，前端正常渲染。
   - 无权限，跳转至权限申请页面。
   - 无权限，展示一个权限申请弹窗，提示用户该功能需要申请权限才能使用，用户点击跳转按钮跳转到权限申请页面申请权限。
   - 无权限，展示一个提示弹窗，提示用户该功能需要管理员主动授权才可使用。

4. 无权限状态下的提示弹窗，是在请求层统一封装的。

#### 2. ECharts 相关

##### 1. 如何二次封装 ECharts，主要考虑哪些点

1. 使用 echarts-for-react 组件作为基础组件。

2. 数据格式化。只需要传入格式化的数据，包括字段、值、颜色等，就可以完成基本的图表渲染。

3. 图表风格统一。举例如下：
   - 图例的位置
   - 折线图的各种样式配置，如横轴和纵轴的样式，比例等。
   - 饼图的各种样式配置，如是否分离、是否设置为环形等。

4. 将 ECharts 通用配置写在组件内部，减少组件使用时 ECharts 传参负担。

5. 统一处理 Loading、Error、Resize 等不同场景下的展示问题。

#### 3. 性能优化

##### 1. 长列表如何做优化

1. 在一个弹窗内展示用户订单相关的数据，每个订单使用的是自定义卡片形式展示。产品要求做成无限滚动模式。在订单数量比较少情况下，滚动查看列表内容还是比较流畅的。但是订单数据比较多的时候，滚动操作就有一些卡顿，操作不是很流畅。

2. 前端的解决方式是使用**虚拟滚动**的方式加载长列表。

##### 1. 用户操作流畅度提升 40%+ 是怎么测量的

1. 使用 React 提供的 Profiler 组件包裹复杂组件，以测量其渲染耗时。

2. 对比优化前后的渲染耗时，所节约的时间，既可以看成用户操作流畅度提升。
